ghee-khatam: a privacy firewall that checks its own output before releasing it

Track 3 · Secret Wards · Member: Ashmit Kumar Verma · Repository: github.com/FierceAdder/Ghee-Khatam

1. In one paragraph

An offline, CPU-only firewall, written in the Python standard library with no models, that cleans hospital records in English, Hindi and Hinglish. It removes personal data, keeps medical values, gives each patient one keyed pseudonym across files and quarantines what it cannot clean. Two ideas set it apart: nothing is published until the finished files have been searched and re-read, and privacy settings were chosen by replaying the published attacks against our own output.

3. How it works

  • Ingestion: CSV, TSV, JSON, FHIR and text in UTF-8, UTF-16 or cp1252, identified by content. Empty, binary, XML, PDF, broken, too deeply nested, symlinked and unknown files are quarantined, never copied. Writers keep the original format.
  • Normalisation: detectors read a view that undoes zero-width characters, Indic digits, homoglyphs, escapes, entities and percent-encoding, with offsets back to the original. Base64 and hex payloads are inspected.
  • Detection: identifier patterns, labels, relation words (S/o, W/o, पुत्र), honorifics, chat senders and layout cues find names that are in no list; name and district lists help. Unfamiliar column headers and JSON keys are typed by what their values look like. A medical veto keeps doctors, hospitals, disease eponyms, the ASHA role, doses and 1-0-1. Identifiers learned in one file are removed from all, file names included.
  • Linkage: union-find over strong identifiers first, then name plus a second clue that fits only one person (birth date, relative, village). A merge is refused if it would join two Aadhaar numbers, sexes, incompatible ages or given names. Devanagari and Latin spellings share a phonetic key. When unsure the answer is null. Pseudonyms are HMAC-SHA256 under RAKSHA_SECRET.
  • Privacy: one keyed date shift per patient (up to 180 days), so intervals stay exact; birth dates removed; ages in bands of 5 to 15 years, chosen from how crowded district-and-sex groups are, 90+ top-coded; village to district; PIN to 3 digits; a diagnosis held by one patient is replaced everywhere in patient records.

4. What a plain PII tool does not do

  • A release gate. The finished values are searched, through disguises and encodings, for every identifier, full name and address phrase detected in the input. Each file is staged, re-read and structure-checked; a failed run publishes no records and says so.
  • Measured privacy. Our replay of attacks A1–A7 and estimate of the utility formula decide each setting; ideas that cost more utility than they saved were dropped.
  • Works without name lists. With every name list removed, no personal data surfaced on the practice data or our first altered copy. New names in scrambled wording still leak (2 of 4 canaries survived a stress test).

6. Security design

  • The secret is read from the environment once, cannot be printed or serialised, and is never written; a run without it is refused.
  • Raw values and the pseudonym map stay in memory. Only redacted bytes are written, inside the output folder, so there is no intermediate store to encrypt. Encryption at rest is not implemented: input, output and swap need an encrypted volume.
  • Logs hold counts, reason codes and file-hash prefixes only. Input is read only; core dumps are disabled; containers run with no network and a read-only root.
  • One bad file is quarantined. A run-wide failure, SIGTERM or an out-of-memory error removes staged files, writes a report marked failed and exits non-zero.

7. Known limitations and next steps

  • The targeted attack still succeeds about half the time: diagnoses shared by two or three patients are kept.
  • A name with no cue, in no list and seen nowhere else is missed, as are most lower-case names. The self-scan cannot find what detection never saw.
  • Typing by values may over-redact unfamiliar columns. A birth date unlabelled everywhere is only shifted.
  • Privacy settings rest on 48 patients. Memory grows with input; about five times the 25 MB case would reach 4 GB (extrapolated).
  • Next: unfamiliar layouts, stronger linking evidence rules, compact in-memory storage.
