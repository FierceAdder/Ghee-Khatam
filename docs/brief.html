ghee-khatam: a privacy firewall that checks its own output before releasing it

Track 3 · Secret Wards · Member: Ashmit Kumar Verma · Repository: github.com/FierceAdder/Ghee-Khatam

1. In one paragraph

An offline, CPU-only firewall (Python; rules plus one small declared model, no LLM) that cleans hospital records in English, Hindi and Hinglish. It removes personal data, keeps medical values, gives each patient one keyed pseudonym across files and quarantines what it cannot clean. Raw and staged data can be encrypted at rest. Two ideas set it apart: nothing is published until the finished files have been searched and re-read, and privacy settings were chosen by replaying the published attacks against our own output.

3. How it works

  • Ingestion: CSV, TSV, JSON, FHIR and text in UTF-8, UTF-16 or cp1252, identified by content. Empty, binary, XML, PDF, broken, too deeply nested, symlinked and unknown files are quarantined, never copied. Writers keep the original format.
  • Normalisation: detectors read a view that undoes zero-width characters, Indic digits, homoglyphs, escapes, entities and percent-encoding, with offsets back to the original. Base64 and hex payloads are inspected.
  • Detection: identifier patterns, labels, relation words (S/o, W/o, पुत्र), honorifics, chat senders and layout cues find names that are in no list; name and district lists help. Unfamiliar headers, JSON keys and form labels are typed by what their values look like across the dataset. Then a fine-tuned IndicBERT (33.4M parameters, MIT) reads free text for names no rule found; it only adds detections and never links records. A medical veto keeps doctors, hospitals, disease eponyms, the ASHA role, doses and 1-0-1. Identifiers learned in one file are removed from all, file names included.
  • Linkage: union-find over strong identifiers first, then name plus a second clue that fits only one person (birth date, relative, village), then a registered phone with a matching name, and rows of one specimen or visit. A merge is refused if it would join two Aadhaar numbers, sexes, incompatible ages or given names. Devanagari and Latin spellings share a phonetic key. When unsure the answer is null. Pseudonyms are HMAC-SHA256 under RAKSHA_SECRET.
  • Privacy: one keyed date shift per patient (up to 180 days), so intervals stay exact; birth dates removed; ages as ranges shared by groups of patients (Mondrian, chosen over 10 secrets of attack replay), 90+ top-coded; village to district; PIN to 3 digits; a diagnosis held by one patient is replaced everywhere in patient records.

4. What a plain PII tool does not do

  • A release gate. The finished values are searched, through disguises and encodings, for every identifier, full name and address phrase detected in the input. Each file is staged, re-read and structure-checked; a failed run publishes no records and says so.
  • Measured privacy. Our replay of attacks A1–A7 and estimate of the utility formula decide each setting; ideas that cost more utility than they saved were dropped.
  • Tested on data we did not tune on. Our generator builds records with exact answer keys and keeps name regions, wordings and layouts held out; a version is judged on those.

6. Security design

  • The secret is read from the environment once, cannot be printed or serialised, and is never written; a run without it is refused.
  • Encryption at rest (AES-256-GCM): files awaiting the audit are on disk only as ciphertext, so a copy of the output folder mid-run holds only ciphertext and audited files. Optional sealed input and encrypted quarantine use a key per file; keys come from the secret and are never written. Raw values live in memory, so swap must be off or encrypted.
  • The run log holds counts and fixed codes only, chained by keyed hashes. Input is read only; core dumps are disabled; containers run with no network and a read-only root.
  • One bad file is quarantined. A run-wide failure or stop signal removes staged files, writes a report marked failed and exits non-zero.

7. Known limitations and next steps

  • Unfamiliar formats: patient linking and name detection are strongest on layouts close to those seen in development. Next: broader linking and name coverage.
  • Targeted re-identification: rare combinations of diagnosis and stay length remain the main residual risk. Next: tune generalisation on larger populations.
  • Hardening: further tests with hostile files and larger inputs.
